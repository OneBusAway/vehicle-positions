# VehiclePositionsKit

Rider-side position reporting for the OneBusAway vehicle-positions server. A
rider says which trip they are on; the SDK registers the device, opens a ride,
streams the device's positions to the server, and reports back what the server
makes of them.

The server never simply believes a rider. It verifies first — matching reported
positions against the trip's shape and schedule, and against a trusted feed
where one exists — and only then publishes the ride as a vehicle position. The
SDK's job is to feed that judgement honestly and to stop reporting the moment
the ride is over.

## Requirements

- iOS 18.0 or later
- Swift 6 (strict concurrency; the package builds in Swift 6 language mode)
- No third-party dependencies

## Installation

Swift Package Manager, from a checkout of this repository next to your app:

```swift
.package(path: "../vehicle-positions/ios/VehiclePositionsKit")
```

For the OneBusAway iOS app, whose project is generated by XcodeGen:

```yaml
packages:
  VehiclePositionsKit:
    path: ../vehicle-positions/ios/VehiclePositionsKit
targets:
  OneBusAway:
    dependencies:
      - package: VehiclePositionsKit
```

A local path is the only form that works today: this repository's root is the Go
server, and the package sits in a subdirectory, which SwiftPM cannot address
over git. Depending on it by URL would need the package split into its own
repository (or a mirror of this subdirectory) — not provided yet.

## Host integration checklist

- **`NSLocationWhenInUseUsageDescription`** in the app's `Info.plist`. When-In-Use
  authorization is enough: the SDK holds a `CLBackgroundActivitySession` for the
  life of a ride, which keeps location running while the app is backgrounded
  without ever asking for Always.
- **`location` in `UIBackgroundModes`**. Without it the background activity
  session cannot keep updates flowing once the app leaves the foreground.
- **Expect the blue indicator.** For as long as a ride is running iOS shows the
  blue location bar or pill. That is the deal When-In-Use plus background
  activity strikes with the rider, and it is correct — say so in your UI.
- **Call `start` from the foreground.** A background activity session started
  while the app is not in the foreground is rejected by Core Location, so begin
  the ride from a user action on screen.
- **Recreate the reporter when the server URL changes.** A reporter is bound to
  one `serverURL` — the region the rider has selected — for its lifetime. On a
  region change, end any ride and build a new reporter.
- **End the ride.** Call `end()` when the rider taps stop, and on app
  termination (`end(reason: .appTerminated)`); the SDK ends rides on its own for
  arrival, stationarity, lost authorization, sustained upload failure and the
  maximum ride duration.

## Usage

```swift
import VehiclePositionsKit

let reporter = RideReporter(
    configuration: RideReporterConfiguration(
        serverURL: region.vehiclePositionsURL,
        appID: Bundle.main.bundleIdentifier ?? "org.onebusaway.iphone",
        appVersion: Bundle.main.appVersion
    )
)

let trip = TripDescriptor(tripID: tripID, startDate: "20260902", destinationStopID: stopID)
for await event in try await reporter.start(trip) {
    switch event {
    case .registered(let riderID): log("registered as \(riderID)")
    case .started(let rideID): log("reporting ride \(rideID)")
    case .progress(let progress): banner.update(state: progress.state, published: progress.published)
    case .warning(let warning): banner.show(warning)
    case .ended(let reason, let summary): banner.finish(reason: reason, summary: summary)
    }
}
// Anywhere else: await reporter.end()               // the rider stopped
//                await reporter.tripStatus(tripID: tripID, startDate: nil)
```

`start` returns a buffered stream, so no event is missed however late iteration
begins, and it finishes when the ride ends. Cancelling the task that awaits
`start` cancels the start: nothing is installed and `CancellationError` is
thrown. Cancellation after `start` has returned does not stop the ride — the
reporter outlives the task that began it — so call `end()` yourself when the
view that started the ride goes away.

## Events

| Event | Meaning |
| --- | --- |
| `.registered(riderID:)` | This device registered (or re-registered) with the server. |
| `.started(rideID:)` | The server opened a ride. |
| `.progress(RideProgress)` | An upload was accepted: state, whether the ride is published, corroboration, points accepted, off-route streak. |
| `.warning(RideWarning)` | Degraded but still running: `.uploadRetrying(attempt:)`, `.accuracyLimited`, `.insufficientlyInUse`. |
| `.ended(RideEndReason, summary:)` | The ride is over; the stream finishes. |

### End reasons

Reported by the client: `userRequested`, `arrived`, `stationary`, `maxDuration`,
`locationUnavailable`, `authorizationDenied`, `networkFailure`, `appTerminated`.

Decided by the server, or local to the SDK: `offRoute`, `contradicted`,
`implausible`, `offSchedule`, `superseded`, `serverRestart`, `idle`.

## Privacy

- The device identifies itself with a **random installation UUID** generated on
  first use and kept in the Keychain (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`,
  never synced). No account, no advertising identifier, no device identifier.
- Positions are **snapped to the trip's route server-side** before anything is
  published, so what other riders see is a point on the route, not the rider's
  exact location.
- Reporting runs only for the duration of a ride the rider started, and the
  stored credentials are the only thing that outlives it.

## Testing

```sh
export DEVELOPER_DIR=/Applications/Xcode-27.0.0-beta.6.app/Contents/Developer
xcodebuild test -scheme VehiclePositionsKit \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
```

For a compile check without running the simulator, build for the simulator
triple — a plain `swift build` targets macOS, which this iOS-only package does
not support:

```sh
swift build --triple arm64-apple-ios18.0-simulator
```

`KeychainCredentialStoreTests` reports itself skipped under `xcodebuild test`:
a SwiftPM test bundle is loaded by the simulator's `xctest` helper, which has no
application identifier, and the keychain answers `errSecMissingEntitlement`
(-34018) to such a process. The suite runs where the keychain is usable — on a
device, or from a host app that embeds these tests.
